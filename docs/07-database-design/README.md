# Document 08 --- Database Design, Schema and Data Persistence

## 1. Purpose

This document describes the PostgreSQL persistence layer used by the
Federated Healthcare Research prototype. It explains the role of the
experiment and metric tables, their known relationships, how experiment
results are persisted, and how the backend exposes those records to the
frontend.

This document is an implementation-oriented description of the schema
established during the project. Where the exact SQLAlchemy column
definition or constraint was not captured in the available
implementation notes, it is explicitly identified as not verified rather
than guessed.

The project is a research prototype. Its database stores experiment
metadata and model-evaluation records; it is not a repository of real
patient records.

## 2. Database Technology and Access Layer

The backend uses:

-   **PostgreSQL** as the relational database.
-   **SQLAlchemy** for ORM models and database access.
-   **Alembic** for schema migration management.
-   **pg8000** as the PostgreSQL Python driver in the Windows
    development environment.
-   **FastAPI** for exposing read-only experiment data through REST
    endpoints.

The database connection is configured through the backend settings
rather than being hard-coded into route handlers. Repository code
performs database queries, while service and API layers shape the
returned data.

### Development environment note

The Windows development environment uses the pure-Python SQLAlchemy path
because of an Application Control restriction affecting compiled
extensions. The environment also uses `DISABLE_SQLALCHEMY_CEXT=1` and a
`postgresql+pg8000` connection URL. This is a local development
workaround, not a requirement of the database design itself.

## 3. Persistence Design

The persistence model separates experiment configuration from the
metrics generated by an experiment.

At a conceptual level:

-   An experiment record describes what was run and its configuration.
-   Centralized evaluation records store the baseline evaluation result.
-   Federated round records store model evaluation and round information
    for each global round.
-   Privacy accounting records store the privacy budget information
    associated with DP training.
-   Client training records store local training measurements for
    individual simulated clients.

This separation allows the API to retrieve experiment metadata and the
relevant result series without rerunning model training.

## 5. `experiments` Table

The `experiments` table is the parent record for a training or
evaluation run. It stores experiment identity, descriptive metadata,
algorithm and dataset details, training configuration, privacy-related
configuration, and lifecycle status.

### Established columns

  -----------------------------------------------------------------------
  Column                              Purpose
  ----------------------------------- -----------------------------------
  `id`                                Experiment identifier

  `name`                              Human-readable experiment name

  `description`                       Experiment description

  `algorithm`                         Algorithm or experiment type

  `dataset_name`                      Dataset used by the experiment

  `partition_strategy`                Client data partition strategy

  `client_count`                      Number of participating simulated
                                      clients

  `num_rounds`                        Federated communication-round
                                      configuration

  `local_epochs`                      Local training epochs per round

  `learning_rate`                     Training learning rate

  `random_seed`                       Configured random seed

  `differential_privacy`              Whether differential privacy is
                                      configured for the run

  `dp_noise_multiplier`               DP noise multiplier configuration

  `dp_max_grad_norm`                  Configured clipping-bound field

  `secure_aggregation`                Secure-aggregation configuration
                                      flag

  `status`                            Experiment lifecycle status

  `created_at`                        Creation timestamp

  `updated_at`                        Last-update timestamp
  -----------------------------------------------------------------------

The experiment identifier is referenced by the experiment's metric
records. The `experiments` table also provides the metadata used by the
experiment list and dashboard summary APIs.

The table's complete SQLAlchemy type and nullability declarations should
be treated as defined by the current model and migration files. This
document does not infer missing type details from the column names.

## 6. `centralized_evaluation_metrics` Table

This table stores the evaluation result for a centralized baseline
experiment.

### Established fields

  -----------------------------------------------------------------------
  Column                              Meaning
  ----------------------------------- -----------------------------------
  `experiment_id`                     Foreign key referencing
                                      `experiments.id`

  `sample_count`                      Number of examples represented by
                                      the evaluation record

  `training_loss`                     Recorded training loss

  `training_accuracy`                 Recorded training accuracy

  `test_accuracy`                     Held-out test accuracy

  `precision`                         Positive-class precision

  `recall`                            Positive-class recall

  `f1_score`                          F1-score

  `sensitivity`                       Sensitivity metric

  `specificity`                       Specificity metric

  `roc_auc`                           ROC-AUC
  -----------------------------------------------------------------------

### Established integrity behavior

-   The experiment relationship is enforced with a foreign key.
-   The experiment is intended to have at most one centralized
    evaluation record; a unique constraint on `experiment_id` was
    established.
-   Range and positive-count checks were added for applicable metric
    values and sample count.

The exact names and SQL expressions of every check constraint are not
reproduced here. Consult the model and migration definitions for the
authoritative expressions.

## 7. `federated_round_metrics` Table

This table stores evaluation and training measurements for each
federated communication round.

### Established fields

  Column                Meaning
  --------------------- ----------------------------------------------
  `experiment_id`       Foreign key referencing `experiments.id`
  `round_number`        Federated communication round
  `client_count`        Number of clients participating in the round
  `total_samples`       Total sample count represented in the round
  `training_loss`       Recorded training loss, when available
  `training_accuracy`   Recorded training accuracy, when available
  `test_accuracy`       Global model test accuracy
  `precision`           Positive-class precision
  `recall`              Positive-class recall
  `f1_score`            F1-score
  `sensitivity`         Sensitivity metric
  `specificity`         Specificity metric
  `roc_auc`             ROC-AUC
  `created_at`          Record creation timestamp

### Established integrity behavior

-   `experiment_id` references the parent experiment.
-   A unique constraint on `(experiment_id, round_number)` prevents
    duplicate records for the same experiment round.
-   The experiment foreign key was configured with cascading deletion.

Some metric values can be unavailable for a particular experiment path.
For example, DP-FedAvg persisted rows intentionally leave
`training_loss` and `training_accuracy` as `NULL`; those values should
not be fabricated or interpreted as zero.

## 8. `privacy_accounting_metrics` Table

The backend persists privacy-accounting records separately from ordinary
model-evaluation metrics. The established table name is
`privacy_accounting_metrics`.

Its records are associated with an experiment and represent
privacy-accounting progress across the DP-FedAvg rounds. The current DP
experiment persisted five privacy records, one for each of its five
rounds.

The API exposes privacy records through the `PrivacyMetricRead` schema,
and the frontend uses them to display epsilon progression and the
configured delta.

### Schema detail boundary

The exact complete SQLAlchemy field list, database types, nullability,
and named constraints for `privacy_accounting_metrics` were not
available in the verified schema notes used to prepare this document.
They are therefore not enumerated here. The model and its applied
Alembic migration are the authoritative sources for those details.

Do not infer that this table stores raw client updates. It stores
privacy-accounting information for the experiment.

## 9. `client_training_metrics` Table

This table stores measurements produced by local client training.

### Established fields

  Column                 Meaning
  ---------------------- -----------------------------------------------
  `id`                   UUID primary key
  `experiment_id`        UUID foreign key to `experiments.id`
  `client_id`            Simulated client identifier; `VARCHAR(100)`
  `partition_strategy`   Client partition strategy; `VARCHAR(30)`
  `sample_count`         Number of local training samples; integer
  `training_loss`        Local training loss; floating-point value
  `training_accuracy`    Local training accuracy; floating-point value
  `epochs_completed`     Number of local epochs completed; integer
  `created_at`           Time-zone-aware creation timestamp; non-null

### Established integrity behavior

-   `id` is the primary key.
-   `experiment_id` references `experiments.id` with `ON DELETE CASCADE`
    and is indexed.
-   A check constraint requires `sample_count > 0`.
-   A check constraint constrains `training_accuracy` to the interval
    from 0 to 1.

### Migration status note

The `client_training_metrics` table was created manually during
development and was not yet represented in the Alembic migration history
at the time this documentation state was recorded. This is an important
schema-management caveat: a database can contain a table that is not
reproducible from the checked-in migration chain.

Before relying on a fresh database setup, reconcile this table with the
migration history so the schema can be created consistently from
migrations. Do not assume that an existing developer database proves a
clean migration-based installation works.

## 10. Foreign Keys and Deletion Behavior

The established metric-table relationship uses `experiment_id` to
associate a result with its parent experiment.

For `federated_round_metrics` and `client_training_metrics`, cascading
deletion was established. Deleting the parent experiment therefore
removes dependent records for those relationships.

The centralized metric table also references the parent experiment. The
exact deletion action for every remaining metric relationship should be
checked in its SQLAlchemy model and migration before documenting it as a
database guarantee.

## 11. Data Persistence Lifecycle

The high-level persistence lifecycle is:

``` mermaid
flowchart TD
    A[Experiment execution] --> B[Create or identify experiment]
    B --> C[Run centralized or federated training]
    C --> D[Collect evaluation metrics]
    C --> E[Collect client training metrics]
    C --> F[Collect privacy accounting metrics]
    D --> G[Persist metric records]
    E --> G
    F --> G
    G --> H[Repository queries]
    H --> I[Experiment service]
    I --> J[FastAPI response schemas]
    J --> K[React dashboard]
```

The training scripts and experiment service are responsible for
coordinating experiment execution and persistence. The API's read paths
retrieve the stored records; opening the dashboard does not itself rerun
model training.

## 13. Read API and Frontend Consumption

The frontend reads persisted experiment data through these API
endpoints:

  ---------------------------------------------------------------------------------------
  Endpoint                                            Purpose
  --------------------------------------------------- -----------------------------------
  `GET /api/v1/experiments`                           Lists recorded experiments

  `GET /api/v1/experiments/summary`                   Returns dashboard summary
                                                      information

  `GET /api/v1/experiments/{experiment_id}`           Retrieves one experiment

  `GET /api/v1/experiments/{experiment_id}/metrics`   Retrieves the experiment's
                                                      associated metrics
  ---------------------------------------------------------------------------------------

The metrics response is assembled using response schemas including:

-   `CentralizedMetricRead`
-   `FederatedRoundRead`
-   `PrivacyMetricRead`
-   `ClientTrainingMetricRead`
-   `ExperimentMetricsResponse`

The experiment service retrieves the client metrics for the selected
experiment and includes them in the experiment metrics response. The
frontend uses these records for experiment details, client training
summaries, model analytics, and privacy visualizations.

The API is read-only for these dashboard use cases. It does not expose
an endpoint that triggers a new training run through the pages
documented here.

## 14. Migration Management

Alembic is used to track schema changes. The development workflow uses
the Python module entry point:

``` powershell
python -m alembic current
python -m alembic history
python -m alembic upgrade head
python -m alembic check
```

Using `python -m alembic` avoids relying on a Windows executable shim
that may not be available in the active environment.

The project has used multiple migration revisions during development. A
single authoritative current revision identifier is intentionally not
stated in this document because the available project notes contain
different revision snapshots from different points in the development
session. Check the current checkout and active database before recording
a revision ID.

A successful migration check indicates that Alembic does not detect
additional operations relative to the metadata it is configured to
compare. It does not, by itself, prove that every manually created
database object is represented in migration history.

## 15. Database Verification

Useful checks during local development include:

1.  Confirm the backend can connect to PostgreSQL.
2.  Confirm the expected experiment records exist.
3.  Confirm metric records are linked to the correct experiment IDs.
4.  Confirm the expected number of federated round and privacy records
    exists.
5.  Confirm nullable fields remain `NULL` when a training path does not
    produce those measurements.
6.  Check foreign-key and uniqueness behavior.
7.  Run Alembic status and migration checks.
8.  Test the experiment API endpoints and compare their responses with
    the persisted records.

For the currently recorded DP-FedAvg experiment, five federated
evaluation records and five privacy-accounting records were persisted.
The experiment metrics endpoint returns the relevant stored information
to the frontend.

## 16. Data Integrity and Interpretation

The database stores measurements; it does not establish that a model is
clinically valid.

Important interpretation rules:

-   A missing metric is not the same as a metric equal to zero.
-   Training metrics and held-out test metrics describe different
    evaluation stages.
-   Client training accuracy is not interchangeable with global model
    test accuracy.
-   Privacy epsilon is an accounting result under a stated adjacency
    definition and accountant configuration, not a generic security
    score.
-   Simulated client identifiers do not represent real hospitals.
-   The current dataset is a public benchmark; no real patient records
    are stored by this prototype.

## 17. Current Limitations and Follow-Up Work

The persistence layer is sufficient for the current dashboard and
recorded experiments, but several improvements would make it more
reproducible and maintainable:

1.  Add `client_training_metrics` to Alembic migrations so a fresh
    database can be built consistently.
2.  Verify the complete privacy metric model and migration definitions,
    then maintain this documentation from those exact definitions.
3.  Add explicit indexes based on measured query patterns, rather than
    adding indexes without evidence.
4.  Store experiment seeds, code revision identifiers, and complete
    preprocessing/partition metadata consistently.
5.  Add database integration tests for foreign keys, uniqueness, check
    constraints, and cascade behavior.
6.  Test a clean database creation and migration sequence in addition to
    upgrading an existing development database.
7.  Keep API response schemas aligned with ORM models and persisted
    data.

These are follow-up recommendations. They should not be interpreted as
features already completed.

## 18. Summary

PostgreSQL is the persistence layer for experiment metadata and the
measurements displayed by the research dashboard. The `experiments`
table acts as the parent record, while centralized evaluation, federated
round, privacy-accounting, and client-training records store results
associated with each run.

The backend uses SQLAlchemy models and repositories to query these
records, service logic to assemble experiment responses, and FastAPI
schemas to expose them to the React frontend. The current dashboard
reads the stored results rather than rerunning model training.

One important migration caveat remains: `client_training_metrics` was
created manually and was not yet represented in Alembic history at the
documented project state. The exact privacy-accounting model field
definitions and the latest migration revision should be verified against
the current source checkout before treating this document as a complete
column-by-column DDL specification.
